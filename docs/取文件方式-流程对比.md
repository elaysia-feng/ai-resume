# 取文件方式：5 种方案的完整流程（Mermaid 对照）

> 这份文档只画**流程**，不对方案做评价。每张图后面附「关键节点」和「实测断点」，
> 用来核对「是不是你想的那种」。

## 参与者约定

| 代号 | 是什么 |
|---|---|
| `U` | 用户 |
| `FE` | 前端 / Electron 渲染层 + preload（**唯一能直接读本机磁盘的进程**） |
| `BE` | 后端 Java（Spring Boot 单体，持有 LLM 编排和工具） |
| `LLM` | MiniMax-M3.1-Flash（Anthropic 兼容端点） |
| `FS` | 本机磁盘（用户选的工作区目录） |

---

## 方案 1：前端直读「选中文件」的全文 → 给后端 LLM

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户
    participant FE as 前端 Electron
    participant FS as 本机磁盘
    participant BE as 后端 Java
    participant LLM as MiniMax

    U->>FE: 勾选 / 拖入文件，选一个提问
    FE->>FS: 读这些文件的全文
    FS-->>FE: 文件内容
    FE->>BE: POST /api/chat/messages<br/>{文件内容 + 问题}
    BE->>LLM: 一次 prompt（含文件全文）
    LLM-->>BE: 回答
    BE-->>FE: SSE text_delta
    FE-->>U: 渲染回答
```

**关键节点**
- **谁读文件**：前端
- **谁决定读什么**：用户（或调用方）事先指定，模型不参与
- **请求次数**：1 次
- **上下文里是什么**：被选中文件的**全文**
- **后端完全不知道文件系统的存在**，也不需要知道

**实测**：10/10（2 次调用 / 1,943 tok / 7.1s），但这是 **oracle**——基准台里文件名是我硬编码的答案。
真实场景下是「用户指定」，用户选对了就满分，选错了就是 0 分。

## 方案 2：前端只给文件树 → LLM 点名 → 前端读 → 回传（多轮）

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户
    participant FE as 前端 Electron
    participant FS as 本机磁盘
    participant BE as 后端 Java
    participant LLM as MiniMax

    U->>FE: 选择工作区目录 + 提问
    FE->>FS: 遍历目录，只取路径
    FS-->>FE: 文件树（路径列表，无内容）
    FE->>BE: POST /api/chat/messages {文件树 + 问题}
    BE->>LLM: prompt（含文件树）
    LLM-->>BE: 我要读 xxx.java
    BE-->>FE: 转发点名
    FE->>FS: 读该文件
    FS-->>FE: 文件内容
    FE-->>BE: 回传文件内容
    BE->>LLM: 追加内容，再问一次
    LLM-->>BE: 继续点名 / 给出答案
    BE-->>FE: SSE
    FE-->>U: 渲染回答
```

**关键节点**
- **谁读文件**：前端（但读哪个是 LLM 说了算）
- **谁决定读什么**：LLM
- **请求次数**：N 次，**每轮都要重发整棵文件树**
- **上下文里是什么**：第 1 轮是文件树，之后是「树 + 已读文件内容」的累积
- **后端也不读磁盘**，纯转发

**实测**：0/10（20 次调用 / **440,970 tok** / 201s）
**断点**：文件树按字母序深度优先，答案模块 `whp-purchase` 排第 9、`whp-temu` 排第 11。
按 148 万字符截断时裁到 `whp-order` 就断了 —— 两个答案文件**连目录都不在树里**，模型只能猜路径。

## 方案 2b：方案 2 的两级树变体（先模块清单，再按模块下发子树）

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户
    participant FE as 前端 Electron
    participant FS as 本机磁盘
    participant BE as 后端 Java
    participant LLM as MiniMax

    U->>FE: 选择工作区目录 + 提问
    FE->>FS: 只扫顶层，算每个模块的条目数
    FS-->>FE: 模块清单（15 行 / 378 字符）
    FE->>BE: {模块清单 + 问题}
    BE->>LLM: prompt
    LLM-->>BE: 我要 whp-temu 模块
    BE-->>FE: 转发
    FE->>FS: 扫 whp-temu 子树，只取路径
    FS-->>FE: 该模块的路径列表
    FE-->>BE: 回传子树
    BE->>LLM: 追加子树
    LLM-->>BE: 我要读 xxx.java
    BE-->>FE: 转发点名
    FE->>FS: 读该文件
    FE-->>BE: 回传内容
    BE->>LLM: 追加内容
    LLM-->>BE: 最终回答（不再点名）
    BE-->>FE: SSE
    FE-->>U: 渲染回答
```

**关键节点**
- **谁读文件**：前端
- **谁决定读什么**：LLM，但**分两级收敛**（先选模块，再选文件）
- **请求次数**：N 次，每轮重发的上下文比方案 2 小一个量级
- **实测**：检索层已验证成功 —— 读到的正是和方案 5 **完全一样的 2 个文件 / 2,892 字节**，
  6 次调用 / 29,663 tok（只有方案 2 的 1/15）。最终评分待额度恢复后补。

## 方案 3：后端直接读取，把内容**全部**给 LLM

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户
    participant FE as 前端 Electron
    participant BE as 后端 Java
    participant LLM as MiniMax
    participant FS as 本机磁盘

    U->>FE: 选择工作区目录 + 提问
    FE->>BE: POST /api/chat/messages {工作区路径 + 问题}
    BE->>FS: 遍历所有文本文件并读全文
    FS-->>BE: 全部内容（140 MB / 1.3 亿字符）
    BE->>LLM: 一次 prompt（全量）
    LLM--xBE: HTTP 400 context window exceeds limit
    BE-->>FE: 报错
    FE-->>U: 失败提示
```

**关键节点**
- **谁读文件**：后端
- **谁决定读什么**：全都要，没有选择
- **请求次数**：1 次（然后被服务端拒）
- **上下文里是什么**：工作区全部文本（140.1 MB / 1.3 亿字符 ≈ 4,360 万 token）

**实测**：服务端 `HTTP 400 invalid params, context window exceeds limit (2013)`
**断点**：即使按最乐观的 16 字符/token 密度算也有 818 万 token，**确定超出上限区间上界**（263 万）。
死路，和模型能力无关。

## 方案 4：后端一次性检索（分段式读取），把 top-k 片段给 LLM

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户
    participant FE as 前端 Electron
    participant BE as 后端 Java
    participant LLM as MiniMax
    participant FS as 本机磁盘

    U->>FE: 选择工作区目录 + 提问
    FE->>BE: POST /api/chat/messages {工作区路径 + 问题}
    BE->>FS: 扫描所有文本文件，切成 chunk
    Note over BE: 本地建 BM25 倒排索引<br/>45,034 个 chunk / 41.9 MB
    BE->>BE: 用问题做 BM25 检索 → top-20 片段
    BE->>LLM: 一次 prompt（20 段片段 + 问题）
    LLM-->>BE: 回答
    BE-->>FE: SSE
    FE-->>U: 渲染回答
```

**关键节点**
- **谁读文件**：后端（**一次性全读**，只是发出去的是片段不是全文）
- **谁决定读什么**：BM25 打分决定，模型不参与
- **请求次数**：1 次
- **上下文里是什么**：20 段相关片段（约 24 KB）+ 片段来自哪些文件的标注

**实测**：3/10（2 次调用 / 15,021 tok / 105.9s）
**断点**：**检索阶段就漏了** —— 答案文件在 BM25 **top-200 都排不进**。
top-8 全被三份总结型长 md 占满（`阅读顺序.md`、`项目架构概览.md`、`API_INTERFACE_SUMMARY.md`）；
加文件名加权后 top-8 只是换成 `TemuDailySalesClient` 之类无关类，仍不含答案文件。
那 3 分是模型从配置文件里**偶然**捞到的 `/ocean1688/auth/callback`，它自己都说「未检索到对应的 @RestController 文件」，Q1 直接 0/5。

## 方案 5：LLM 直接绑定读取能力，自己决定什么时候读什么

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户
    participant FE as 前端 Electron
    participant BE as 后端 Java
    participant LLM as MiniMax
    participant FS as 本机磁盘

    U->>FE: 选择工作区目录 + 提问
    FE->>BE: POST /api/chat/messages {工作区路径 + 问题}
    BE->>LLM: prompt（问题 + 3 个工具定义）<br/>read_local_file / search_in_files / list_dir

    LLM->>BE: tool_use: search_in_files("TemuShopAuthInfoController")
    BE->>FS: 按文件名扫全树
    FS-->>BE: 命中路径
    BE-->>LLM: tool_result
    LLM->>BE: tool_use: read_local_file("whp-temu/.../TemuShopAuthInfoController.java")
    BE->>FS: 读文件
    FS-->>BE: 文件内容
    BE-->>LLM: tool_result
    LLM->>BE: tool_use: list_dir("whp-temu/temu.biz/...")
    BE->>FS: 列目录
    BE-->>LLM: tool_result
    LLM-->>BE: 纯文本最终回答（不再有 tool_use）
    BE-->>FE: SSE text_delta
    FE-->>U: 渲染回答
```

**关键节点**
- **谁读文件**：后端（**工具执行在 Java 进程里**）
- **谁决定读什么**：LLM 自己
- **请求次数**：N 次，**每次只带上一轮的工具结果**，不重发大段上下文
- **上下文里是什么**：增量 —— 模型点了什么才给什么
- **前端完全不知道模型要读哪个文件**

**实测**：10/10（16 次调用 / 读 5 个文件 12,476 字节 / 21,600 tok / 37s）
**优点**：唯一不依赖「事先知道答案文件」的满分方案；读取字节最省；天然支持多轮追问。
**代价**：token 比方案 1 多（多轮工具往返）。

## 现网 Java 实现对应哪一套

```mermaid
flowchart LR
    subgraph MIX["现网 Java chat 包（混合形态）"]
        T1["read_local_file<br/>= 方案 1 的读法"]
        T2["search_in_files<br/>= 方案 5 的找法"]
        T3["list_dir<br/>= 方案 5 的探法"]
    end
    T1 --> MIX2["统一走 tool calling 协议<br/>= 方案 5 的编排"]
    T2 --> MIX2
    T3 --> MIX2
```

> 也就是说：**方案 5 已经能覆盖方案 1 的场景**。
> 用户明确指定文件 → 模型直接调 `read_local_file`（和方案 1 一样 1 次读完），
> 只是多了一层模型往返，不是多读了文件。
